# `gantt (1).html` 分析與優化建議（不改變功能）

## 1) 檔案現況摘要

此檔案為單頁式工具，整合了：

- UI 介面（Tailwind + 大量自訂 CSS）
- Excel 讀取/匯出（`xlsx`、`exceljs`）
- 甘特圖日期欄產生
- 欄位凍結、欄寬調整、右鍵選單
- 篩選、高亮、統計分析、變更檢視等互動

目前整體可看出功能成熟、互動完整，但結構偏向「所有邏輯集中在單一 HTML」，隨功能增加，維護成本會快速上升。

---

## 2) 優點

1. **功能整合度高**  
   單檔即可運作，部署成本低，使用者只需開啟頁面上傳 Excel 即可操作。

2. **UI 回饋完整**  
   提供錯誤訊息、彈窗、統計結果、變更檢視、行列高亮等互動，使用體驗佳。

3. **有考慮資料可讀性**  
   例如 sticky 表頭、欄位裁切、省略號、統計表固定表頭、數字右對齊等。

4. **功能細節豐富**  
   包含欄位狀態保存（隱藏/寬度）、樹狀展開收折、條件高亮限制等，顯示需求理解深入。

---

## 3) 主要缺點 / 風險

1. **單檔過大、責任混雜（HTML/CSS/JS 全集中）**  
   當前檔案同時負責結構、樣式、狀態、資料處理與事件協調，不利多人協作與測試。

2. **樣式重複與覆蓋鏈複雜**  
   存在多段 `<style>`，且同一 selector 有多次定義（例如 `.highlight` 被重設與再覆蓋），後續調整容易誤傷。

3. **全域狀態變數過多**  
   例如 `currentDataArray`、`generatedDateColumns`、`dateChanges`、`manualDateCellTexts` 等都在全域，狀態關聯複雜，除錯難度高。

4. **函式職責偏大**  
   如 `renderTable()` 涉及資料處理、DOM 建立、樣式與事件綁定，變更任一需求可能連動多處。

5. **外部 CDN 依賴缺少版本/安全治理策略**  
   雖已有版本號，但缺少 SRI（Subresource Integrity）與失效備援策略，企業內網或嚴格環境可能不可用。

6. **可及性（a11y）仍可加強**  
   互動元件（按鈕、彈窗、右鍵選單）可再補 ARIA 屬性與鍵盤導覽行為，提升無障礙與一致性。

---

## 4) 不改功能的修改方向（建議實作順序）

> 下列改法皆屬「重構與整理」，目標是**維持既有功能與輸出一致**。

### Phase A：先做低風險整理（可立即做）

1. **拆分檔案**
   - `gantt (1).html`：保留 DOM 結構
   - `assets/css/app.css`：搬移全部樣式
   - `assets/js/app.js`：搬移邏輯

2. **樣式去重與命名整理**
   - 合併重複規則（特別是 `.highlight`、modal 相關）
   - 將「共用樣式」與「特例覆蓋」分區，降低 `!important` 使用

3. **加上設定常數區**
   - 將魔法字串（如顏色、欄寬、class 名稱）集中到 `const CONFIG = {}`

### Phase B：重構程式結構（中風險）

1. **模組化邏輯（檔內分層也可）**
   - `dataService`: 讀 Excel、欄位索引、資料正規化
   - `tableRenderer`: 畫表格、套欄寬、sticky、樹狀縮排
   - `ganttService`: 產生日期欄、甘特上色
   - `statsService`: 統計表與明細
   - `uiController`: 事件綁定與彈窗開關

2. **全域狀態收斂為單一 store**
   - 以 `const state = { ... }` 集中
   - 提供 `setState/patchState` 或明確更新函式

3. **大型函式切小**
   - 例如 `renderTable()` 拆成：
     - `buildHeader()`
     - `buildBodyRows()`
     - `applyColumnStates()`
     - `bindTableEvents()`

### Phase C：品質保障（中低風險）

1. **建立最小自動化測試**
   - 單元測試：日期欄生成、欄位索引推斷、統計計算
   - E2E 測試：上傳檔案→產生甘特→匯出 Excel

2. **加上程式碼規範工具**
   - ESLint + Prettier
   - Stylelint（若 CSS 規模持續增長）

3. **可觀測性**
   - 對關鍵流程加 `debug logger`（開關式）
   - 錯誤訊息統一處理，避免 `console` 分散

---

## 5) 可直接套用的「不改功能」清單

- [ ] 將 inline `<style>` 全搬到 `app.css`
- [ ] 合併重複的 `.highlight` 與 modal 背景規則
- [ ] 將全域變數集中到 `state` 物件
- [ ] 將 `renderTable()` 拆分為 3~5 個純函式
- [ ] 事件綁定集中到 `bindEvents()`
- [ ] 對外部 CDN 增加 SRI 或提供離線備援
- [ ] 補齊彈窗與右鍵選單 ARIA 屬性
- [ ] 增加最小測試（至少涵蓋日期欄與統計）

---

## 6) 預期效益

完成上述重構後，在不改功能下可得到：

- 維護成本降低（讀 code 路徑更短）
- 新功能開發速度提升（模組邊界清楚）
- 回歸風險降低（有測試保護）
- 佈署與安全性更可控（CDN 依賴治理）

---

## 7) 結論

這份 `gantt (1).html` 的功能完整度高，已具備實務可用性；目前最大問題不是「功能不足」，而是「可維護性與可擴充性」開始成為瓶頸。建議採取「先整理、再模組化、最後補測試」的三階段策略，能在**不改變既有功能**前提下，顯著提升品質與長期開發效率。
